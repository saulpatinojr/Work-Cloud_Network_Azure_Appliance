### Fixed
- **`350`/`360` fail when the drift plan itself fails.** Both drift workflows ran `terraform plan -detailed-exitcode ... || EXIT=$?` and then tested only for exit 2, so a plan that *errored* (exit 1 — a missing backend, an expired credential, a provider fault) was read as "no drift" and the job went green. That is the failure mode `TODO.md` → T-105 describes from the other side: the check must be loud before its delivery can be. Exit 0 is still clean and exit 2 still a drift warning; any other exit now fails the job with the plan's own exit code, for both the platform and the workload plan. Mirrors the AWS appliance, whose `350`/`360` were written this way (its `CHANGELOG.md` recorded the sibling gap). Shared workflow change — no other repository is affected; the core owns no drift workflow.
- **The workload storage account's firewall window.** The application storage account has been deny-by-default since `TODO.md` T-106, and `azurerm_storage_account_static_website` is provisioned and refreshed over the data plane, but no workflow allow-listed the runner's IP the way the Key Vault steps do — from any runner not already in `ip_rules`, the workload plan/apply and the portal publish fail with `403` (`AuthorizationFailure`). `210-deploy` (plan and apply), `350`/`360-drift` and `320-publish-portal` now add the runner's public IP before touching the account and remove it in an `always()` step, resolving the account from Terraform state (`storage_account_name` output) rather than restating the naming rule. The first apply of an environment has no account to open, so `210` passes the IP as `TF_VAR_deploy_runner_ip` → workload variable `deploy_runner_ip` → storage module `bootstrap_ip_rules`, which the account is created with; the existing `ignore_changes` on `ip_rules` makes that a creation-time value only. Azure-only wiring (Secrets Manager and S3 have no equivalent), so nothing changes in the sibling.

### Changed
- **The core is now `Work-Cloud_Network_Core`** (core `TODO.md` T-509, 2026-09-18). The application code and the image builds moved from the project's original repository, `Work-Cloud_Network_Assessment`, into a dedicated internal core repository; the original is archived. `CLAUDE.md` and `README.md` point at the new repository and its Wiki, and the `CORE_REPO` variable — the only place `230-image-update` learns where the build manifest lives — must be set to the new name by the repository admin (`REVIEW.md` R-005). Nothing else changes: the image tag scheme, the manifest schema, the `cna-image-published` dispatch and the runtime environment contract are the same, so a deployed environment is unaffected. Mirrored in the sibling appliance in the same change set.
- **Every workflow runs on GitHub-hosted runners (`ubuntu-latest`).** `300 · Validate` moved first (its jobs need no cloud credentials, and a new repository had no runner registered, which left the first pull request's checks queued indefinitely); the deploy and operations workflows — `000`, `100`, `210`, `220`, `230`, `320`, `330`, `340`, `350`, `360` — follow now that the self-hosted runner the original repository used is retired. Nothing in them needs a private network: cloud access is OIDC, the migrator runs as a Container App job inside Azure, and every job that reads Key Vault over the data plane already opens a per-run firewall window for the runner's own public IP (`340 · Sync Local Keys` gains the same window — it read the deny-by-default vault without one). `scripts/bootstrap-runner.sh` (the VPS runner provisioner) and its `.secrets.baseline` entry are removed. Mirrored in the sibling appliance.
